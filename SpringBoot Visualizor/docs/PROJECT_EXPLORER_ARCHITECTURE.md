# Project Explorer: architecture, decisions and phased plan

Status: **approved direction; nothing is implemented.** This document records the approved architecture. Each stage below needs its own review
and approval before it starts.

SpringLab then has two complementary products:

* **Curated Labs** teach how Spring technologies work through controlled experiments (REST lifecycle, JWT, JPA, JDBC, Microservices).
  They are preserved unchanged.
* **Project Explorer** helps a user understand how an *actual* Spring Boot codebase is structured and behaves. It is a separate module, not a
  replacement for the labs, and not a more elaborate simulator.

A more visual simulator is not runtime visualization. Project Explorer must always show whether a fact was observed, read from source, inferred,
or explained.

## 1. Intended experience

1. Connect a local project or upload a ZIP.
2. Discover controllers, services, repositories, entities, DTOs, configuration, dependencies and REST endpoints.
3. Generate an architecture map from the actual source.
4. Select an endpoint and see its request lifecycle.
5. Tie every stage to a source file, class, method and line range.
6. Show how data changes shape: JSON, DTO, entity, database record, response.
7. Trigger a real request (local projects only) and observe methods, SQL, exceptions and the response.
8. Give a 5W1H explanation at every stage.
9. Offer What-If explanations of changing or removing a component.

## 2. Provenance: four labels

| Label | Meaning |
|---|---|
| `CAPTURED` | Directly observed at runtime |
| `SOURCE` | Directly extracted from source code or configuration |
| `DERIVED` | Inferred from available evidence |
| `CONCEPTUAL` | Explanatory or hypothetical; not established by source or runtime evidence |

Every node, edge and explanation keeps its basis. Every relationship also carries a confidence classification (for example *certain* /
*possible* / *unresolved*). A static call edge means "the source allows this call", not "this call happened".

Rules:

* The analyzer never invents a controller-to-service or service-to-repository relationship. If it cannot resolve one, the symbol is reported as unresolved.
* Unresolved symbols and unsupported patterns are visible in the UI, with the reason.
* Every discovered class, method, endpoint and relationship has a source reference (file, line range) where one exists.
* Members generated by Lombok are shown as **generated**, never as if they were written in the source.
* Static analysis and runtime tracing are separate subsystems; they meet only through the shared project model.
* The AI/LLM is never the source of truth for execution. Explanations are authored knowledge-base text filled with real names.

## 5. Architecture

```
React "Project Explorer" (new route, shared learning framework)
      │ REST
SpringLab backend: ingestion API ── analyzer-core (pure Java library, no Spring)
      │                               JavaParser + symbol solver → Project Model (JSON)
      │
      │ runtime collector ◄── OTLP ── OpenTelemetry Java agent on the TARGET app (local projects only)
      ▼       merges spans onto the Project Model
 evidence-merged scenario
```

* `analyzer-core` is a separate Maven module with golden tests against a fixture corpus.
* Static analysis and runtime tracing are separate; the **Project Model** is the only contract between them.
* Incremental analysis is desirable eventually and is not required for the MVP.

## 6. Execution and ingestion policy (approved)

* Uploaded ZIPs are **static-analysis only** and are never executed on the SpringLab server.
* Local execution applies only to the project the user explicitly selects on their own machine. There is no remote arbitrary-code execution.
* ZIP handling: extraction limits (entries, total size, per-file size, compression ratio), path-traversal protection, no symbolic links, reject unsafe names.
* Dependency resolution must not run Maven lifecycle plugins of an uploaded project. Dependencies are read from declared coordinates and resolved
  without executing project code; if that is impossible the symbols stay unresolved and are reported.
* Secrets: values of secret-like configuration keys are never displayed or stored.
* Only directories the user explicitly selects are read. No scanning of unrelated directories, databases or personal files.

## 7. Runtime approach

Start with the **OpenTelemetry Java agent**. Stage 1 must verify, not assume, that it can capture the application method calls we need, beyond
HTTP and JDBC: for example via its method-include configuration, an extension, or ByteBuddy. If generic method instrumentation needs a custom
extension or ByteBuddy code, document the limitation and compare alternatives before committing. A custom agent is **not** built prematurely.
Branch and line capture are later, optional research.

## 8. Lombok

Handled by explicit analysis rules for `@Data`, `@Getter`, `@Setter`, `@RequiredArgsConstructor`, `@AllArgsConstructor`, `@NoArgsConstructor` and
`@Builder`. Generated members are marked generated. Any annotation or configuration that cannot be resolved accurately is reported as a limitation.

## 9. MVP scope (stages 1 to 3)

In: one Maven Spring Boot 3 project on Java 17+, Spring MVC, Spring Data JPA, constructor and field injection; endpoints, beans, DI graph, controller →
service → repository chains; source references; a templated 5W1H; unresolved/unsupported report; static only.
Out: Gradle, Kotlin, multi-module builds, WebFlux, messaging, running the project, value tracking, React linking, what-if re-execution.

## 10. Order of work

1. **Browser acceptance** of the existing SpringLab, and fixing defects found. No new features until it is complete.
2. **Microservices Lab Experiment/Observe rework**: the diagram is visible while configuring and running an experiment, with replay, packet
   interactions, payload inspection and state changes where recorded evidence supports them. No SSE streaming without a demonstrated need.
3. **Project Explorer** stages below.

| Stage | Deliverable | Verified by |
|---|---|---|
| 1. Spike (report only) | Evaluate JavaParser, Maven symbol resolution, Lombok handling, endpoint discovery, dependency resolution and OpenTelemetry method instrumentation, on SpringLab and user-selected projects. No analyzer implementation | Written findings, reviewed |
| 2. Static model and endpoints | Project Model schema, stereotypes, endpoints, DI graph, repositories, entities | Golden tests |
| 3. Ingestion and Explorer UI | Local-path (allowlist) connect and static-only ZIP upload; architecture map; endpoint list; source viewer; static lifecycle diagram with 5W1H | Tests and browser acceptance |
| 4. Data shape view | JSON → DTO → entity → response, with confidence | Golden tests |
| 5. Runtime tracing MVP | Agent recipe, collector, run correlation, Try-it panel (explicit target), evidence merged on the static graph | Integration tests, browser acceptance |
| 6. Exceptions, branches, values | Exception paths, opt-in redacted values, line coverage (research) | Spike first |
| 7. What-if | Rule-based static what-if, labelled conceptual; re-execution on a patched copy deferred | |
| 8. React linking | Match `axios`/`fetch` calls to endpoints (approximate) | |

## 11. Risks

1. Executing untrusted code: avoided by the execution policy above.
2. Lombok and generated code: rules above; unsupported cases reported.
3. Symbol resolution depends on the classpath; partial failure is expected and must be visible.
4. Interface dispatch, proxies, events, `@Async`, reflection and lambdas defeat static certainty; edges carry a confidence classification.
5. Branch and line capture per request requires serialised requests; stage 6 research.
6. Captured values may contain personal data or secrets; shapes by default, redaction, opt-in values.
7. Agent compatibility with the target's Java version, and overhead.
8. An authoritative-looking tool can mislead; the evidence basis must be visible on every element.

## 12. Test corpus

SpringLab itself is not enough to show the analyzer generalises. The corpus also includes Spring Boot projects the user explicitly selects, chosen
to cover different controller, service, repository, DTO, entity and injection patterns. The project directories must be confirmed with the user
before anything is read. Nothing outside them is scanned.
