# 01 · Basic Security: SecurityFilterChain, Form Login, HTTP Basic and BCrypt

An employee portal secured with **Spring Security 6**:
- **Public:** status information that anyone can read.
- **Protected:** employee data that needs a login.
- **REST API:** uses **HTTP Basic**.
- **Admin dashboard:** a browser page that uses a **login form**.

Passwords are stored only as **BCrypt hashes**.

The configuration uses the Spring Security 6 style: `SecurityFilterChain` **beans**, with no `WebSecurityConfigurerAdapter` (that class was removed in Spring Security 6).

## Tech

Java 17 · Maven · Spring Boot 3.5.6 · **Spring Security 6.5** · Spring Web · JUnit 5 + MockMvc + spring-security-test · Postman. No database (the users are in memory).

## How the security works

### 1. Default behaviour (before any configuration)

Adding `spring-boot-starter-security` alone already locks the application. This was observed by running with the `defaults` profile, which switches this project's configuration off:

```text
Using generated security password: <random UUID>
This generated password is for development use only. ...

GET /api/public/hello                      -> 401   (even the "public" endpoint)
GET /api/employees  (Accept: text/html)    -> 302 -> http://localhost:8080/login
GET /login                                 -> 200   "Please sign in" (page generated by Spring)
```

Spring Boot's defaults:
- every URL needs a login
- one user called `user`, with a new random password printed at each start
- a generated login page and logout
- HTTP Basic
- CSRF protection

`DefaultSecurityBehaviourTest` checks this automatically.

### 2. The filter chain

Spring Security is a chain of **servlet filters** that runs **before** the request reaches any controller:
1. The servlet container calls one filter, `DelegatingFilterProxy`.
2. That passes the request to Spring's `FilterChainProxy`.
3. `FilterChainProxy` looks at the URL and picks the **first** `SecurityFilterChain` whose `securityMatcher` matches.
4. Only that chain's filters run.

This project has two chains (`SecurityConfig`):

| Order | Chain | Matches | Login | Session | CSRF | Unauthenticated → |
|---|---|---|---|---|---|---|
| `@Order(1)` | `apiChain` | `/api/**` | HTTP Basic | **stateless** | **off** | 401 JSON |
| `@Order(2)` | `browserChain` | everything else | login form (+ Basic) | HTTP session | **on** | 302 to `/login` |

The real filter lists, from the application's DEBUG log at startup:

```text
Will secure /api/** with filters:
  DisableEncodeUrlFilter, WebAsyncManagerIntegrationFilter, SecurityContextHolderFilter, HeaderWriterFilter,
  LogoutFilter, BasicAuthenticationFilter, RequestCacheAwareFilter, SecurityContextHolderAwareRequestFilter,
  AnonymousAuthenticationFilter, SessionManagementFilter, ExceptionTranslationFilter, AuthorizationFilter

Will secure any request with filters:
  DisableEncodeUrlFilter, WebAsyncManagerIntegrationFilter, SecurityContextHolderFilter, HeaderWriterFilter,
  CsrfFilter, LogoutFilter, UsernamePasswordAuthenticationFilter, BasicAuthenticationFilter,
  RequestCacheAwareFilter, SecurityContextHolderAwareRequestFilter, AnonymousAuthenticationFilter,
  ExceptionTranslationFilter, AuthorizationFilter
```

The API chain has **no `CsrfFilter`** and no `UsernamePasswordAuthenticationFilter` (no form). The browser chain has both.

**Walk-through of `GET /api/employees` with `Authorization: Basic alice:Alice@123`:**

| Filter | What it does here |
|---|---|
| `SecurityContextHolderFilter` | starts with an empty `SecurityContext` for this request |
| `HeaderWriterFilter` | adds security headers (`X-Content-Type-Options`, `X-Frame-Options`, cache control ...) |
| `BasicAuthenticationFilter` | decodes the header and passes `alice` / `Alice@123` to the `AuthenticationManager` (details below the table). On success it stores the result in the `SecurityContext`. |
| `AnonymousAuthenticationFilter` | only acts when nobody logged in: puts an "anonymous" authentication in the context |
| `ExceptionTranslationFilter` | wraps the rest: turns security exceptions into 401 (entry point) or 403 (access-denied handler) |
| `AuthorizationFilter` | checks the URL rules: `/api/employees/**` → `authenticated()` → allowed |
| → `EmployeeController` | runs; `Authentication` can be injected (see `/api/profile`) |

Inside `BasicAuthenticationFilter`, the `AuthenticationManager` hands the credentials to a `DaoAuthenticationProvider`, which:
1. calls `PortalUserDetailsService.loadUserByUsername("alice")`
2. compares the password with the stored hash, using `BCryptPasswordEncoder.matches`

The DEBUG log of that request:

```text
Securing GET /api/employees
Set SecurityContextHolder to UsernamePasswordAuthenticationToken [Principal=...User [Username=alice,
    Password=[PROTECTED], Enabled=true, ... Granted Authorities=[ROLE_USER]], ... SessionId=null]
Secured GET /api/employees
```

Without credentials:
1. `AnonymousAuthenticationFilter` sets an anonymous user.
2. `AuthorizationFilter` denies access.
3. `ExceptionTranslationFilter` calls the **entry point**, which returns the 401 JSON.

### 3. Matcher order and why it matters

```java
.requestMatchers("/api/public/**").permitAll()
.requestMatchers(HttpMethod.GET, "/api/employees/count").permitAll()   // specific first ...
.requestMatchers("/api/employees/**").authenticated()                   // ... general after
.anyRequest().authenticated()                                           // always last
```

- **First match wins:** the rules are checked **top to bottom**, and the first one that matches decides.
- **Specific before general:** `/api/employees/count` also matches `/api/employees/**`, so the specific rule must come first. If the two lines were swapped, the head count would need a login, because the general rule would match first.
- **`anyRequest()` must be last:** Spring Security 6 refuses to start otherwise.
- **The same applies to chains:** that's why the narrow `/api/**` chain has `@Order(1)`, and the catch-all browser chain `@Order(2)`.

The proof is `matcherOrder_specificPublicRuleBeforeTheGeneralRule`: `/api/employees/count` returns 200 without a login, while `/api/employees/1` returns 401.

### 4. Two ways to log in

| | HTTP Basic (`/api/**`) | Form login (`/admin/**`) |
|---|---|---|
| How credentials arrive | `Authorization: Basic base64(user:password)` on **every** request | **once**, POSTed from the login form |
| Afterwards | nothing is remembered (stateless) | an HTTP session; the browser sends the `JSESSIONID` cookie |
| Filter | `BasicAuthenticationFilter` | `UsernamePasswordAuthenticationFilter` |
| Good for | API clients, scripts, Postman, testing | people using a browser |
| Logout | not needed: just stop sending the header | `POST /logout` invalidates the session |

**Form-login flow (as followed by the Postman collection):**
1. **Not logged in:** `GET /admin/dashboard` → **302** to `/login`. The original request is saved in the session.
2. **Open the form:** `GET /login` returns the **custom login page**. It contains a hidden `_csrf` token.
3. **Log in:** `POST /login` (username, password, `_csrf`) → **302** to `/admin/dashboard?continue` and a `JSESSIONID` cookie. Spring Security 6 adds `?continue` to mark that the saved request should be restored.
4. **Use the session:** `GET /admin/dashboard` with the cookie → **200**.
5. **Log out:** `POST /logout` with `_csrf` → **302** to `/login?logout`. The session is invalidated and the cookie deleted.
   - A client that does not ask for HTML (`Accept: */*`) gets **204 No Content** instead of a redirect.
   - `GET /logout` is not a logout, so a link on another site cannot log users out.

**Custom failure handling:**
- **Browser:** a wrong form login goes back to `/login?error`, which shows *"Invalid username or password."*
- **API:** `JsonSecurityErrorHandlers` returns a 401 JSON body instead of an empty one, with the same message whether the password was wrong or the user does not exist. That way, attackers can't use the response to find which usernames exist.

### 5. Authentication vs authorization

- **Authentication**, *who are you?*, is checking an identity: the username and password are verified, and an `Authentication` object is stored in the `SecurityContext`. A failure gives **401 Unauthorized**, despite the name.
- **Authorization**, *what may you do?*, is checking that a known user is allowed: `AuthorizationFilter` compares the user's authorities with the rule for the URL. A failure gives **403 Forbidden**.

In this project, `alice` **is authenticated** (correct password) but **not authorized** for `/admin/dashboard` (needs ROLE_ADMIN), so she gets **403**, not a login page.

### 6. Passwords: BCrypt, and hashing vs encryption

**Hashing vs encryption:**

| | Hashing (BCrypt) | Encryption (e.g. AES) |
|---|---|---|
| Direction | **one-way**: the password cannot be recovered | two-way: decrypt with the key |
| Key | none | a key that must be stored and protected |
| Login check | hash the typed password, compare | decrypt and compare (the key could leak every password) |
| Use for passwords | **yes** | **no** |

**Why BCrypt is a good password hash:**
- **Salt:** every hash includes a random salt, so the same password gives a different hash each time (`samePasswordGivesDifferentHashes_becauseOfTheSalt`), and precomputed tables do not work.
- **Deliberately slow:** the **strength** (cost) is log2 of the work. Each +1 doubles the time, for us once per login and for an attacker for each of billions of guesses.
- **Self-describing:** the cost is stored in the hash (`$2a$12$...`), so the strength for new hashes can be raised later without breaking existing ones.

Only hashes are stored (`application.properties`). `PortalUsersProperties` **refuses to start** if a value is not a BCrypt hash, so a plain-text password cannot slip in by accident. `PasswordStorageTest.aPlainTextPasswordInTheConfiguration_isRejected` checks this.

**Strength experiment** (`BcryptStrengthExperimentTest`, measured on this PC):

| Strength | Time for one hash |
|---|---|
| 8 | 44 ms |
| 10 | 140 ms |
| 12 | 536 ms |
| 14 | 2,161 ms |

Every +2 is about 4× slower. **12** was chosen:
- A login takes about half a second, which users don't notice.
- An attacker can test only about 2 guesses per second per CPU core.
- 14 would make every login wait over 2 seconds.

### 7. CSRF: when is disabling it appropriate?

**The attack:** CSRF (cross-site request forgery) works because a browser **automatically** sends cookies. A malicious page can submit a hidden form to `http://localhost:8080/logout` or `/login`, and the browser attaches the victim's `JSESSIONID`. Spring Security's defence is a secret token that the real page includes in every form, and that a foreign page cannot read.

| Chain | Authentication | CSRF | Why |
|---|---|---|---|
| browser | session cookie | **ON** | cookies are sent automatically, so the token is needed; `formLogin_withoutCsrfToken_isForbidden` proves it |
| API | `Authorization` header on every request, no session | **OFF** | the browser never adds this header on its own, and no cookie exists to abuse |

Disabling CSRF is appropriate **only** when the API is truly stateless and does **not** authenticate with cookies. A REST API that stored its login in a cookie would need CSRF protection again.
